# Michael Wang — Photography Portfolio

A fast, static photography portfolio built with [Astro](https://astro.build). It replaces the old Wix site and runs on free hosting (Vercel) at [www.haozhewang.com](https://www.haozhewang.com). The only running cost is the domain, about $10–15 a year.

- `/`: hero slideshow followed by the project grid (`/#work`), with category filters
- `/projects/<slug>`: project intro, masonry gallery, lightbox, and previous/next project links
- `/about`: portrait, bio and contact form
- `/portfolio` redirects to `/#work`. Old Wix URLs redirect as well (see `vercel.json`).

For the move off Wix, follow **[MIGRATION.md](./MIGRATION.md)**.

## Stack

- **Astro 5**, static output, plain CSS, no UI framework
- **sharp** (through Astro's `<Image>`/`<Picture>`) turns the originals into responsive WebP (AVIF for the hero and portrait) with `srcset` and lazy loading
- **@astrojs/sitemap** generates `sitemap.xml`
- Contact form posts directly to **Formspree** or **Web3Forms**, so there is no backend
- Hosted on **Vercel** and deployed from GitHub

## Local development

You need **Node.js 22** (20 works too). Install it from [nodejs.org](https://nodejs.org) or with `nvm install 22`.

```bash
npm install          # once
npm run dev          # http://localhost:4321, reloads as you edit
npm run build        # checks photos, then builds the site into dist/
npm run preview      # serves dist/ locally to test the production build
npm run check:photos # lists oversized images and missing covers
npm run placeholders # creates placeholder images in empty photo folders
```

`npm run build` runs `check:photos` first. Its warnings never stop the build. To make warnings fail the run, use `npm run check:photos -- --strict`.

## Photo workflow

The `photos/` folders hold the photos imported from the Wix Media Manager export (resized to a 3000 px long edge, JPEG quality 85, metadata stripped). To add or replace photos:

1. **Export from Lightroom:** JPEG, sRGB, long edge **3000–4000 px**, quality **~85**. Each file should come out at roughly 1–4 MB. Larger files make the build slower without improving how the site looks, and the checker warns about anything over 5 MB.
2. **Name the files for their order:** `01.jpg`, `02.jpg`, … `20.jpg`. They sort numerically, so `10.jpg` comes after `09.jpg`. Pad numbers with zeros for clarity.
3. **Pick the cover** with `cover:` in `index.md`, e.g. `cover: "07.jpg"`. It is the square grid tile (center-cropped) and the image shown when the link is shared, and it stays in the gallery. A separate file named `cover.jpg` also works; that one is left out of the gallery.
4. **Hero and portrait:** landscape images in `photos/_home/` (shown in filename order) and one portrait in `photos/_about/`. Their descriptions live in `alt.json` next to them:
   ```json
   { "01.jpg": "Neon-lit Tokyo side street at night, a lone pedestrian under signs" }
   ```
5. **Alt text per photo is optional.** Photos without it are described as "<Project title>, photograph N". Add entries under `alt:` in `index.md` if you want better descriptions.
6. Run `npm run check:photos` to catch oversized files or a missing cover.

`npm run placeholders` only writes to folders that have **no** images, so it never overwrites your photos. HEIC, TIFF and RAW files are not supported, so export JPEGs.

## Adding a new project

1. Create `photos/<slug>/`. Use lowercase with hyphens, for example `photos/night-markets/`. The folder name becomes `/projects/night-markets`.
2. Add `cover.jpg` and the gallery images (see above).
3. Create `photos/<slug>/index.md`:

```markdown
---
title: "Night Markets"
order: 14                     # position in the grid (1 = first)
year: 2025                    # shown on the grid tile
date: "May 3rd, 2025"         # free text, shown on the project page
location: "Taipei"
type: "Photography"
categories: ["Street", "Travel"]   # any of: Street, Events, Portraits, Travel, Food
cover: "cover.jpg"
coverAlt: "Steam rising from a food stall lit by bare bulbs"
alt:
  01.jpg: "Vendor flipping skewers over a charcoal grill"
  02.jpg: "Crowd moving between stalls under red lanterns"
draft: false                  # true hides the project from the site
---

One to three short paragraphs about the project. Plain Markdown.
```

Only `title` and `order` are required. Categories must match the list in `src/site.config.ts` (`categories`). To add a category, add it there first. You can also write the `alt` map in one line: `alt: { "01.jpg": "…", "02.jpg": "…" }`.

## Contact form

The form posts directly to a form service, which emails you each submission. Pick one of the two:

**Formspree** (free tier: 50 submissions a month)
1. Sign up at [formspree.io](https://formspree.io) and create a form. Use `michael.wang8111@gmail.com` as the target email.
2. Copy the endpoint, which looks like `https://formspree.io/f/abcdwxyz`.
3. Set `PUBLIC_FORM_ENDPOINT=https://formspree.io/f/abcdwxyz`.

**Web3Forms** (free tier: 250 submissions a month, no account needed)
1. Go to [web3forms.com](https://web3forms.com), enter your email and get an access key by email.
2. Set `PUBLIC_FORM_ENDPOINT=https://api.web3forms.com/submit`.
3. Set `PUBLIC_FORM_ACCESS_KEY=<your access key>`. The key is public by design.

**Where to set the variables:**
- Locally, create a `.env` file in the project root (it is not committed):
  ```
  PUBLIC_FORM_ENDPOINT=https://formspree.io/f/abcdwxyz
  PUBLIC_FORM_ACCESS_KEY=
  ```
- On Vercel, go to **your project → Settings → Environment Variables** and add them for **Production** (and Preview, if you want).
- Then **redeploy** (Deployments → ⋯ → Redeploy, or push a commit). `PUBLIC_*` values are baked in at build time, so changing a variable has no effect until the next build.

Send a test message after deploying and check that it arrives, including in your spam folder. Confirm the first submission if the service asks you to.

## Deploying to Vercel

The site is hosted on **Vercel** (free Hobby plan) at **https://www.haozhewang.com**. Every push to the `site` branch (the repo's default) redeploys it, and other branches and pull requests get preview URLs.

1. **Push this project to GitHub** (the repo can be private):
   ```bash
   git remote add origin https://github.com/<you>/michael-wang-portfolio.git
   git push -u origin main
   ```
2. On [vercel.com](https://vercel.com), go to **Add New → Project**, import the repo and keep the detected settings. `vercel.json` already sets the framework to **Astro**, the build command to `npm run build` and the output directory to `dist`.
3. **Settings → Environment Variables** (Production): add `PUBLIC_FORM_ENDPOINT` / `PUBLIC_FORM_ACCESS_KEY` (see Contact form). `PUBLIC_SITE_URL` is optional; it defaults to `https://www.haozhewang.com` in `astro.config.mjs`.
4. **Settings → Build and Deployment → Node.js Version:** choose **22.x**.
5. **Deploy.** A full build resizes every photo and takes a minute or two.

`vercel.json` also holds the **redirects** for old Wix URLs and the **caching/security headers** (`/_astro/*` files are cached for a year).

## Custom domain (haozhewang.com)

The domain is connected through Vercel:

1. Project → **Settings → Domains**: both `haozhewang.com` and `www.haozhewang.com` are listed, with `www.haozhewang.com` as the primary address and the bare domain redirecting to it. If you ever flip that (bare domain primary), change the default URL in `astro.config.mjs` to match, so canonical links never point at a redirect.
2. DNS: if the domain uses Vercel nameservers (bought through Vercel, or nameservers pointed at `ns1.vercel-dns.com` / `ns2.vercel-dns.com`), the records are automatic. If DNS is hosted elsewhere, add the `A` record for `@` and the `CNAME` for `www` exactly as the Domains page shows them.
3. HTTPS certificates are issued automatically once DNS resolves.
4. If the domain ever changes, update the default in `astro.config.mjs` (or set `PUBLIC_SITE_URL`) and redeploy. Canonical URLs, Open Graph links, `sitemap.xml` and `robots.txt` use it.

### Alternatives

Cloudflare Pages and Netlify also work for free (build `npm run build`, output `dist`). They don't read `vercel.json`, so the redirects and headers would have to move to `public/_redirects` and `public/_headers`.

## Podcast (Market Brief)

`/podcast` lists the Market Brief episodes, `/podcast/<slug>` shows one (player, show notes, tickers, sources), and `/podcast/rss.xml` is the feed for podcast apps. Episodes come from the brief pipeline in `~/Market Briefs` (see `HANDOFF.md` there for the file format):

```bash
npm run podcast:import   # copy new or changed episodes, then npm run build
MARKET_BRIEFS_DIR=/path/to/briefs npm run podcast:import
```

The script reads `daily/*-episode.md` and `weekly/*-episode.md`, validates the frontmatter, and copies each episode to `src/content/podcast/<date>.md` (weekly: `<date>-weekly.md`) and its MP3 to `public/podcast/audio/<same slug>.mp3`. Unchanged files are skipped. A missing MP3 or bad field stops the run before anything is copied. Chart screenshots are never published. Channel title and description are `podcast` in `src/site.config.ts`; the audio cache header is in `vercel.json`.

**Full brief on each episode page.** The import also copies each episode's full brief to `src/content/briefs/`: the published brief page (`daily/<date>-page.html` or `weekly/<date>-page.html`, the page the email links to) as `<slug>.html`, or the Markdown brief as `<slug>.md` when there is no page. The episode page shows everything in it, in the same order (for a daily: Article Takeaways, The Through-Line, Numbers Worth Remembering, Top Takeaways, charts, Sources; the weekly adds its scoreboard and numbered sections). Episodes without a brief fall back to the short show notes. The publishers' charts (FT, WSJ, CNBC, The Information, Ornn) are never published: the page lists each one's caption with a link to its source, and the screenshots stay in the owner-only research view (see below).

**Original charts.** Each episode's frontmatter can list up to four `charts:` (format and rules in `~/Market Briefs/procedures/episode-charts.md`): line charts of public-domain U.S. government data (Treasury yields, the Fed's target rate, EIA oil prices, BLS CPI and unemployment, the trade-weighted dollar) and bar charts of figures confirmed by an official source or two publications. Each chart is drawn at build time as SVG (`src/components/charts/`), ends at the episode's date so old episodes never change, and goes right after the text under the brief heading named in `after`. There are no default charts: an episode with no relevant data has none. Commercial data (Ornn H100, DRAMeXchange) stays off the public site until its licence is verified.

```bash
npm run series:update   # fetch/validate the government series into src/data/series/ (backfilled from 2000)
npm test                # unit tests for the series validation
```

`series:update` reads FRED's public CSVs (no API key). Each update is validated before it replaces the committed file (dates, plausible ranges, no silent rewrites of old history, small recent revisions only); a series that fails keeps its last good data. The list of series is `src/data/series.json`: only add series whose original source is a U.S. government agency.

**Privacy check.** `npm run build` ends with `scripts/check-public-dist.mjs`, which fails the build if `dist/` contains a research page, an image under `podcast/`, a screenshot-like file name, or (on Michael's Mac) any file with the same bytes as a saved screenshot.

**Daily publishing** runs from `~/Market Briefs/scripts/publish-site.mjs` (data → import → build → commit → push, idempotent, logged to `~/Market Briefs/logs/publish-site.log`).

## Private research view (/research)

An owner-only area at `https://www.haozhewang.com/research` shows each brief beside the publisher screenshots saved while reading it (FT, WSJ, CNBC, The Information, Ornn). It is the only part of the site that isn't static: `api/research.js` is one Vercel function, and `vercel.json` rewrites `/research/*` to it. The public pages, RSS and sitemap never link to it, `robots.txt` disallows it, and the build check fails if any of it reaches `dist/`.

- **Sign-in:** GitHub OAuth (state + PKCE). Only the GitHub account whose numeric id is `RESEARCH_OWNER_GITHUB_ID` gets in. The GitHub token is used once to read the account id and then revoked.
- **Session:** a `__Host-` cookie, HMAC-signed, HttpOnly, Secure, SameSite=Lax, valid 12 hours. Sign out is a POST from the page.
- **Images:** every image request is checked (`/research/img/...` returns 401 without a valid session) and streamed from a **private** Cloudflare R2 bucket through the function. There is no public bucket URL and no shareable signed link. Responses are `private, no-store`, `noindex`, `no-referrer`, with a strict Content-Security-Policy.
- **Fails closed:** until every setting below exists, every `/research` URL answers 503.
- **What gets uploaded:** `~/Market Briefs/scripts/upload-research.mjs` (run by the 7:20 stage after publishing, separately from it) uploads briefs and metadata, and screenshots only from publishers set to `true` in `~/Market Briefs/config/research.json`. All are `false` until you've confirmed each publisher's terms allow keeping copies in your own private cloud storage (the file records what was checked on 2026-10-20). Screenshots not uploaded show as captions on the remote view.
- **On this Mac only:** `npm run research:local` serves the same view at http://127.0.0.1:4330/research with every screenshot, straight from `~/Market Briefs/research-store`. No upload and no sign-in; it only listens on 127.0.0.1.
- **Tests:** `npm test` (sessions, OAuth, image auth, path checks, SigV4 against AWS's example) and `node ~/Market\ Briefs/scripts/test-upload-research.mjs` (uploader against a fake S3 server).

### One-time setup (about 15 minutes)

1. **Cloudflare R2** (free tier: 10 GB, no egress fees). In the Cloudflare dashboard: R2 → Create bucket, e.g. `haozhewang-research`. Leave **Public access** off: no r2.dev URL and no custom domain.
2. **Two R2 API tokens** (R2 → Manage R2 API Tokens → Create API token), each limited to that bucket:
   - *Object Read only* → for Vercel. Note the Access Key ID and Secret Access Key.
   - *Object Read & Write* → for this Mac. Store its secret in the Keychain:
     `security add-generic-password -s r2-research-upload -a r2 -w` (it prompts for the secret).
3. **`~/Market Briefs/config/research.json`**: fill in `r2.accountId` (Cloudflare account id), `r2.bucket` and the read-write `r2.accessKeyId`.
4. **GitHub OAuth app** (GitHub → Settings → Developer settings → OAuth Apps → New): homepage `https://www.haozhewang.com`, callback `https://www.haozhewang.com/research/callback`. Note the Client ID and generate a Client secret. Your numeric user id: `https://api.github.com/users/<your-login>` → `id`.
5. **Vercel → Project → Settings → Environment Variables** (Production): `RESEARCH_GITHUB_CLIENT_ID`, `RESEARCH_GITHUB_CLIENT_SECRET`, `RESEARCH_OWNER_GITHUB_ID`, `RESEARCH_SESSION_SECRET` (`openssl rand -base64 48`), `R2_ACCOUNT_ID`, `R2_BUCKET`, `R2_READ_ACCESS_KEY_ID`, `R2_READ_SECRET_ACCESS_KEY`. Redeploy.
6. Run `node ~/Market\ Briefs/scripts/upload-research.mjs` once; it confirms the bucket refuses anonymous reads. Then sign in at `/research`.

## Performance notes

- Images are resized and converted at build time. Upload originals at 3000–4000 px; anything bigger only slows builds.
- Every image is rendered with fixed dimensions or aspect ratios, so the layout doesn't shift while loading. The first hero image is preloaded and the rest load lazily.
- `/_astro/*` files are hashed and cached for a year (`vercel.json`).
- Builds get slower as photos are added, since each image is processed. A full build of the current ~200 photos takes about a minute; Vercel's Hobby plan allows 45 minutes per build.
- Check performance with Lighthouse (Chrome DevTools → Lighthouse, mobile) after real photos are in. The target is 95+.

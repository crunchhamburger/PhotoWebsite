# Michael Wang — Photography Portfolio

A fast, static photography portfolio built with [Astro](https://astro.build). It replaces the old Wix site and runs on free hosting (Cloudflare Pages). The only running cost is the domain, about $10–15 a year.

- `/`: hero slideshow followed by the project grid (`/#work`), with category filters
- `/projects/<slug>`: project intro, masonry gallery, lightbox, and previous/next project links
- `/about`: portrait, bio and contact form
- `/portfolio` redirects to `/#work`. Old Wix URLs redirect as well (see `public/_redirects`).

For the move off Wix, follow **[MIGRATION.md](./MIGRATION.md)**.

## Stack

- **Astro 5**, static output, plain CSS, no UI framework
- **sharp** (through Astro's `<Image>`/`<Picture>`) turns the originals into responsive AVIF/WebP with `srcset` and lazy loading
- **@astrojs/sitemap** generates `sitemap.xml`
- Contact form posts directly to **Formspree** or **Web3Forms**, so there is no backend
- Hosted on **Cloudflare Pages** and deployed from GitHub

## Local development

You need **Node.js 22** (20 works too). Install it from [nodejs.org](https://nodejs.org) or with `nvm install 22`.

```bash
npm install          # once
npm run dev          # http://localhost:4321, reloads as you edit
npm run build        # checks photos, then builds the site into dist/
npm run preview      # serves dist/ locally to test the production build
npm run check:photos # lists oversized images and missing alt text
npm run placeholders # creates placeholder images in empty photo folders
```

`npm run build` runs `check:photos` first. Its warnings never stop the build. To make warnings fail the run, use `npm run check:photos -- --strict`.

## Photo workflow

The `photos/` folders currently hold **generated placeholders** (dark gradients labelled "PLACEHOLDER"). To swap in the real photos:

1. **Delete the placeholder files** in a folder (`cover.jpg`, `01.jpg` … `08.jpg`). Keep `index.md`.
2. **Export from Lightroom:** JPEG, sRGB, long edge **3000–4000 px**, quality **~85**. Each file should come out at roughly 1–4 MB. Larger files make the build slower without improving how the site looks, and the checker warns about anything over 5 MB.
3. **Name the files for their order:** `01.jpg`, `02.jpg`, … `20.jpg`. They sort numerically, so `10.jpg` comes after `09.jpg`. Pad numbers with zeros for clarity.
4. **Add a `cover.jpg`.** It is the square grid tile (center-cropped) and the image shown when the link is shared. It can be a copy of one of the gallery images. To use a different file, set `cover:` in `index.md`. The cover is left out of the gallery.
5. **Hero and portrait:** put 2–5 landscape images in `photos/_home/` and one portrait in `photos/_about/`. Add alt text in `alt.json` next to them:
   ```json
   { "01.jpg": "Neon-lit Tokyo side street at night, a lone pedestrian under signs" }
   ```
6. Run `npm run check:photos` and add the alt text it lists as missing.

`npm run placeholders` only writes to folders that have **no** images, so it never overwrites your photos. HEIC, TIFF and RAW files are not supported, so export JPEGs.

## Adding a new project

1. Create `photos/<slug>/`. Use lowercase with hyphens, for example `photos/night-markets/`. The folder name becomes `/projects/night-markets`.
2. Add `cover.jpg` and the gallery images (see above).
3. Create `photos/<slug>/index.md`:

```markdown
---
title: "Night Markets"
order: 14                     # position in the grid (1 = first)
year: 2025                    # shown on the grid tile
date: "May 3rd, 2025"         # free text, shown on the project page
location: "Taipei"
type: "Photography"
categories: ["Street", "Travel"]   # any of: Street, Events, Portraits, Travel, Food
cover: "cover.jpg"
coverAlt: "Steam rising from a food stall lit by bare bulbs"
alt:
  01.jpg: "Vendor flipping skewers over a charcoal grill"
  02.jpg: "Crowd moving between stalls under red lanterns"
draft: false                  # true hides the project from the site
---

One to three short paragraphs about the project. Plain Markdown.
```

Only `title` and `order` are required. Categories must match the list in `src/site.config.ts` (`categories`). To add a category, add it there first. You can also write the `alt` map in one line: `alt: { "01.jpg": "…", "02.jpg": "…" }`.

## Site settings

Edit `src/site.config.ts`:

| Setting | What it does |
|---|---|
| `email` | Shown in the footer and the contact section |
| `phone`, `showPhone` | Phone number; it stays hidden unless `showPhone: true` |
| `instagram` | Full Instagram URL for the header icon (confirm the handle) |
| `name`, `tagline`, `description` | Wordmark and the default SEO description |
| `categories` | Filter buttons above the grid |

## Contact form

The form posts directly to a form service, which emails you each submission. Pick one of the two:

**Formspree** (free tier: 50 submissions a month)
1. Sign up at [formspree.io](https://formspree.io) and create a form. Use `michael.wang8111@gmail.com` as the target email.
2. Copy the endpoint, which looks like `https://formspree.io/f/abcdwxyz`.
3. Set `PUBLIC_FORM_ENDPOINT=https://formspree.io/f/abcdwxyz`.

**Web3Forms** (free tier: 250 submissions a month, no account needed)
1. Go to [web3forms.com](https://web3forms.com), enter your email and get an access key by email.
2. Set `PUBLIC_FORM_ENDPOINT=https://api.web3forms.com/submit`.
3. Set `PUBLIC_FORM_ACCESS_KEY=<your access key>`. The key is public by design.

**Where to set the variables:**
- Locally, create a `.env` file in the project root (it is not committed):
  ```
  PUBLIC_FORM_ENDPOINT=https://formspree.io/f/abcdwxyz
  PUBLIC_FORM_ACCESS_KEY=
  ```
- On Cloudflare, go to **Workers & Pages → your project → Settings → Variables and Secrets** and add them for **Production** (and Preview, if you want).
- Then **redeploy** (Deployments → ⋯ → Retry deployment, or push a commit). `PUBLIC_*` values are baked in at build time, so changing a variable has no effect until the next build.

Send a test message after deploying and check that it arrives, including in your spam folder. Confirm the first submission if the service asks you to.

## Deploying to Cloudflare Pages

1. **Create a GitHub repository** (it can be private) and push this project:
   ```bash
   git init && git add -A && git commit -m "Portfolio site"
   git branch -M main
   git remote add origin https://github.com/<you>/michael-wang-portfolio.git
   git push -u origin main
   ```
2. On [dash.cloudflare.com](https://dash.cloudflare.com) (free account), go to **Workers & Pages → Create → Pages → Connect to Git** and select the repo.
3. Build settings:
   - Framework preset: **Astro**
   - Build command: `npm run build`
   - Build output directory: `dist`
4. Environment variables (Production):
   - `NODE_VERSION` = `22`
   - `PUBLIC_SITE_URL` = `https://<project>.pages.dev` for now; change it to your domain later
   - `PUBLIC_FORM_ENDPOINT` / `PUBLIC_FORM_ACCESS_KEY` (see above)
5. **Save and Deploy.** The site goes live at `https://<project>.pages.dev`. Every push to `main` redeploys it automatically, and other branches get preview URLs.

`public/_redirects` (old Wix URLs) and `public/_headers` (caching and security headers) are applied by Cloudflare automatically.

## Custom domain

1. In the Pages project, go to **Custom domains → Set up a custom domain** and enter `yourdomain.com`. Then add `www.yourdomain.com` too.
2. DNS:
   - **Domain bought from Cloudflare Registrar, or already using Cloudflare nameservers:** the DNS records are created automatically. Nothing else to do.
   - **Domain elsewhere (Namecheap, Squarespace, GoDaddy, Wix…):**
     - *Recommended:* add the domain to Cloudflare (free plan) and change the **nameservers** at your registrar to the two Cloudflare gives you. Cloudflare Pages only supports the apex domain (`yourdomain.com` without `www`) when DNS is on Cloudflare.
     - *Alternative (www only):* at your current DNS provider, add `CNAME www → <project>.pages.dev`. You can only point the bare apex there through a provider that supports CNAME flattening or ALIAS/ANAME records, and Cloudflare may not verify it. Use the nameserver option if you can.
3. HTTPS certificates are issued automatically, usually within minutes (up to 24 hours for DNS changes).
4. Set `PUBLIC_SITE_URL=https://yourdomain.com` in the Pages environment variables and **redeploy**. Canonical URLs, Open Graph links and `sitemap.xml` depend on it.
5. **Redirect `www` to the apex** so there is only one canonical address. In the Cloudflare dashboard for the domain, go to **Rules → Redirect Rules** and create a rule that matches hostname `www.yourdomain.com` and sends a 301 to `https://yourdomain.com${path}` with the query string preserved. Bulk Redirects or a Page Rule work too. The `www` DNS record must be proxied (orange cloud).
6. Optional: uncomment the `*.pages.dev` `noindex` block in `public/_headers` so Google only indexes your domain.

### Alternatives

- **Netlify:** import the repo with build `npm run build`, publish `dist`. `_redirects` and `_headers` use the same format. Netlify Forms could replace Formspree, but that needs a `data-netlify` attribute on the form.
- **Vercel:** import the repo; it detects Astro automatically. `_redirects`/`_headers` are **not** read, so the redirects would need moving to `vercel.json`.

## Performance notes

- Images are resized and converted at build time. Upload originals at 3000–4000 px; anything bigger only slows builds.
- Every image is rendered with fixed dimensions or aspect ratios, so the layout doesn't shift while loading. The first hero image is preloaded and the rest load lazily.
- `/_astro/*` files are hashed and cached for a year (`public/_headers`).
- Builds get slower as photos are added, since each image is processed. Cloudflare's free tier allows 500 builds a month and a 20-minute build limit, which is plenty for this site.
- Check performance with Lighthouse (Chrome DevTools → Lighthouse, mobile) after real photos are in. The target is 95+.
